If you would rather write than talk, that is not a limitation to work around. It
is a specialisation, and a large part of the remote market is written by design
because written support is easier to run across time zones.

## The work types

| Type                      | What you actually do                | Written by nature because |
| ------------------------- | ----------------------------------- | ------------------------- |
| Inbox management          | Triage, draft replies, file, flag   | Email is already text     |
| Chat / live support       | Answer customers in a chat window   | The channel is text       |
| Ticket handling           | Read, categorise, resolve, escalate | Tickets are records       |
| Online research           | Find, verify, write up              | The output is a document  |
| Data entry and cleaning   | Enter, check, standardise           | The output is a file      |
| Documentation             | SOPs, checklists, meeting notes     | The output is written     |
| Calendar and scheduling   | Book, confirm, reschedule           | Confirmations are written |
| File and drive management | Structure, share, maintain          | The work is in a drive    |

The pattern: **asynchronous work is written work.** A client who needs support
across several time zones cannot rely on calls, so they hire for writing.

## A day in writing

A typical written-support day is a sequence of sessions rather than a continuous
conversation:

- **First pass, early:** clear the overnight queue. Triage, answer what you can,
  turn the rest into tasks. This is where time zones help you — the client's day
  starts after you have already worked.
- **Second pass, mid-morning:** the substantive work. Drafts, research, data,
  documentation. Messages closed.
- **Third pass, end of your day:** send what is ready, update the statuses, write
  the one-line handover so the client wakes up to progress rather than questions.

The skill is batching. A written-support role fails when you check messages
continuously, because every message interrupts the work that the messages are
about.

## Being honest about working in writing

Say it in the first conversation, as a strength rather than an apology:

> "I work in writing — email, chat and documents. That suits asynchronous work
> well, and it means everything I do is documented. If you need an occasional
> call, I can join one, but I won't be the person running it."

Two things worth agreeing early:

- **What happens when something is genuinely urgent?** A written-only arrangement
  needs one channel with a shorter response window, or an agreed "call me" signal.
  Without it, every problem becomes a reason for a call.
- **How feedback arrives.** Written feedback on written work is easy; verbal
  feedback that you have to transcribe is not. Ask for comments in the document.

## What not to do

Do not describe yourself as "not good at talking" — describe the work you do. Do
not accept a role that is secretly a call-centre job and then try to avoid the
calls. Do not let a client assume you are available by voice if you are not; it is
much easier to say so at the start than to decline a call later.

## Practice

Pick two work types from the table and write, for each, what a client would see
from you over one working day: what arrives, what you send back, and what the
client has to do.
