A standard operating procedure is not bureaucracy. It is the difference between a
task that takes you ten minutes and a task that takes ten minutes plus a
conversation, every time it happens.

## What is worth writing down

Not everything. Write down a task when **any** of these is true:

- It happens more than once a month.
- More than one person does it.
- Getting it wrong is expensive, embarrassing or hard to undo.
- You had to ask someone how to do it the first time.

If none of those apply, a checklist is enough — or nothing is.

## Writing steps someone else can follow

The test is a competent stranger. They know how to use a computer and they know
nothing about this client.

Each step should be **one action**, and should say **what success looks like**:

```text
1. Open the shared drive and go to Clients / Acme Co / 01 Inbox.
   You should see one folder per week, named YYYY-WW.

2. For each file in the week folder, rename it to
   YYYY-MM-DD_AcmeCo_<description>.<ext>.
   Do not change the extension. If a file has no clear date, use the date it was
   received and note that in the log.

3. Move the renamed file to 02 Active / <project>.
   If you cannot tell which project it belongs to, put it in 05 Unsorted and add
   a line to the log.
```

Three things make the difference between a procedure and a wish:

- **Exact locations**, not descriptions. "The client folder" is not a location.
- **The decision points named.** Every "if you cannot tell" is where a real person
  gets stuck, and it is the part most procedures omit.
- **What to do when it goes wrong.** Where does an exception go? Who do you tell?
  A procedure with no exception path gets abandoned the first time something
  unusual happens.

## Keeping it alive

A document nobody updates is worse than no document, because it is trusted and
wrong. Two habits:

- **Date it and put your name on it.** `Updated 2026-10-05 by …` tells the reader
  how much to trust it.
- **Update it when you use it.** The moment you notice a step is out of date is
  the only moment you will remember what changed.

Where it lives matters too: next to the work, not in a documentation folder
nobody opens. A procedure for the client drive belongs in the client drive.

## What not to do

Do not write a procedure from memory a month after you last did the task — do it
while you work, and write down the steps you actually took, including the
detours. Do not write one for a task nobody repeats. Do not use a procedure to
avoid a conversation about whether the process should change.

## Practice

Take a task you do repeatedly and write it up in the format above. Then give it to
someone who has never done it and watch where they hesitate — those are the steps
you skipped.
